# packages/kernel/src/execution/dbos-port.ts

## Facts
- agentQueue(depth) and runQueue(depth) in dbos-port.ts name depth-partitioned DBOS queues (agents:<d>, runs:<d>) registered up to config.maxDepth at launch, so a gate-waiting parent at depth d never competes for the same queue slot as the depth d+1 children it is waiting on. {w29jis01 @packages/kernel/src/execution/dbos-port.ts#agentQueue #architecture-current}
- createDbosPort in packages/kernel/src/execution/dbos-port.ts implements the @orc/contracts ExecutionPort interface by registering two DBOS SDK workflows, orcStep and orcRun, via DBOS.registerWorkflow. {dcabgozd @packages/kernel/src/execution/dbos-port.ts#createDbosPort #architecture-current}
- makeCheckpoint in dbos-port.ts wraps DBOS.runStep so a checkpoint's drafted events are appended inside the same EventLog transaction as the checkpointed effect, each under a deterministic idempotency key, so a crash-retry returns committed records instead of duplicating them. {s1tcn6t0 @packages/kernel/src/execution/dbos-port.ts#createDbosPort.makeCheckpoint #architecture-current}
- makeOperation in dbos-port.ts wraps DBOS.runStep around the operation journal (beginOperation/completeOperation/failOperation) so a completed operation node short-circuits on recovery with its stored redacted value instead of re-running the external effect. {coqexlu2 @packages/kernel/src/execution/dbos-port.ts#createDbosPort.makeOperation #architecture-current}
- runWorkflow's wave scheduler launches every step returned by readySteps(plan,done,failed,started) in packages/kernel/src/execution/interpreter.ts for the current wave via DBOS.startWorkflow, then Promise.all's the whole wave before recomputing readiness, rather than continuously scheduling as individual steps complete. {8lneign5 @packages/kernel/src/execution/dbos-port.ts#createDbosPort.runWorkflow @packages/kernel/src/execution/interpreter.ts#readySteps #architecture-current}

## Why
- A gate recv polls for an hour rather than seconds, because every recv records a durable row even on expiry and recovery replays each sequentially (a 60 s poll is about 1,440 rows a day), while sysdb.recv re-checks cancellation every 10 s regardless. {dh4l03el @packages/kernel/src/execution/dbos-port.ts#GATE_POLL_SECONDS}
- appendRunInit appends run_started idempotently and re-checks task status inside the same transaction before moving to running, so DBOS re-executing init on resume is a no-op instead of a fixed-key idempotency conflict that bricks the task at running. {3hfvoht9 @packages/kernel/src/execution/dbos-port.ts#appendRunInit}
- createDbosPort sets the executor id through DBOS.setConfig, because DBOS recovers pending workflows per executorID and defaults every process to local, so two runtimes would each recover the other's in-flight steps. {qnp54fd2 @packages/kernel/src/execution/dbos-port.ts#createDbosPort.executorId}
- projectState throws on an unlaunched port instead of folding the whole log, because every caller runs inside or after launch so null is a wiring bug that a silent fallback would hide as a slowdown. {q9xagkd1 @packages/kernel/src/execution/dbos-port.ts#createDbosPort.projectState}
- Every status except running gets a new run index, because a blocked run returns normally so DBOS marks its deterministic workflow SUCCESS and re-running would re-attach and replay the cached result, making orc run silently do nothing; the status comes from the fold, not DBOS. {s6d3f1qy @packages/kernel/src/execution/dbos-port.ts#createDbosPort.runIndexFor}
- The run workflow contains an uncaught error by moving the task to blocked under the locked re-check, because otherwise the task stays running with an ERROR workflow that orc retry re-attaches to and rethrows forever. {dadpqf9k @packages/kernel/src/execution/dbos-port.ts#createDbosPort.runWorkflow}
- Wave-at-a-time scheduling (not continuous) is deliberate: DBOS binds started child workflows positionally by (callerID, callerFunctionID) rather than by the requested workflowID, so replay launch order must exactly match first-run launch order or two steps can swap DBOS handles and the run stalls forever. {iyq8oiso @packages/kernel/src/execution/dbos-port.ts#createDbosPort.runWorkflow #architecture-current}
- A run with no explicit cwd inherits its parent's run cwd, else the project directory, never a per-step scratch dir, because an empty scratch workspace is one no repo task can succeed in. {xq9au2le @packages/kernel/src/execution/dbos-port.ts#createDbosPort.startRunAt}
- The step workflow skips output re-verification when step_completed already committed, because after a crash before DBOS recorded the step result the workspace may have changed and re-hashing would conflict with the committed receipts and flip a durable success into failed. {1b582eiz @packages/kernel/src/execution/dbos-port.ts#createDbosPort.stepWorkflow}
- A split counts as consumed only once this workflow handed it to a gate, not when it resolved, because the router appends split_resolved before sending, so a child that outran its parent has a message waiting and filtering on resolved dropped its summary. {gg3x926j @packages/kernel/src/execution/dbos-port.ts#createDbosPort.stepWorkflow.consumed}
- A continuation round after round 0 prefixes its checkpoint names and operation ids with the round, because the loop names them by iteration, which restarts at 1 each round, and a reused key would replay round 0's recorded model call as round 1's answer. {aqjml5d6 @packages/kernel/src/execution/dbos-port.ts#createDbosPort.stepWorkflow.driveRound}
- A split gate intersects an explicit request with this attempt's unconsumed splits, because an unknown or foreign id can never receive a message and would wedge recv forever; an empty intersection resumes with an empty list. {thsqihmc @packages/kernel/src/execution/dbos-port.ts#createDbosPort.stepWorkflow.driveRound.targets}
- Only an auditor's signalled failure is a verdict, because an auditor judges other steps' work and a retry meets the same completed siblings and concludes the same, while a worker's fresh attempt redoes its own work and can succeed. {7r4ddhkz @packages/kernel/src/execution/dbos-port.ts#createDbosPort.stepWorkflow.failClass}
- The continuation loop has no request_iterations tool, because an agent asked whether it wants more budget always says yes, so the grant lives in the runtime where spend is already enforced. {9uwan4pz @packages/kernel/src/execution/dbos-port.ts#createDbosPort.stepWorkflow.grant}
- driveGenerator always calls gen.return() in a finally, because an abandoned async generator's finally never runs, so a port throw at a gate would leak the step's write-claims and poison later retries in a long-lived process. {fejds86s @packages/kernel/src/execution/dbos-port.ts#driveGenerator}
- The run-status transition reads and appends in one locked transaction, because makeCheckpoint opens a separate transaction for its drafts, so an orc cancel could commit in between and be overwritten by running to done (fold is last-seq-wins). {wqgigebf @packages/kernel/src/execution/dbos-port.ts#stampIfRunning}
