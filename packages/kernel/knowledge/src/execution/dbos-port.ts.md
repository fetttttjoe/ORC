# packages/kernel/src/execution/dbos-port.ts

## Facts
- agentQueue(depth) and runQueue(depth) in dbos-port.ts name depth-partitioned DBOS queues (agents:<d>, runs:<d>) registered up to config.maxDepth at launch, so a gate-waiting parent at depth d never competes for the same queue slot as the depth d+1 children it is waiting on. {w29jis01 @packages/kernel/src/execution/dbos-port.ts#agentQueue #architecture-current}
- createDbosPort in packages/kernel/src/execution/dbos-port.ts implements the @orc/contracts ExecutionPort interface by registering two DBOS SDK workflows, orcStep and orcRun, via DBOS.registerWorkflow. {dcabgozd @packages/kernel/src/execution/dbos-port.ts#createDbosPort #architecture-current}
- makeCheckpoint in dbos-port.ts wraps DBOS.runStep so a checkpoint's drafted events are appended inside the same EventLog transaction as the checkpointed effect, each under a deterministic idempotency key, so a crash-retry returns committed records instead of duplicating them. {s1tcn6t0 @packages/kernel/src/execution/dbos-port.ts#makeCheckpoint #architecture-current}
- makeOperation in dbos-port.ts wraps DBOS.runStep around the operation journal (beginOperation/completeOperation/failOperation) so a completed operation node short-circuits on recovery with its stored redacted value instead of re-running the external effect. {coqexlu2 @packages/kernel/src/execution/dbos-port.ts#makeOperation #architecture-current}
- runWorkflow's wave scheduler launches every step returned by readySteps(plan,done,failed,started) in packages/kernel/src/execution/interpreter.ts for the current wave via DBOS.startWorkflow, then Promise.all's the whole wave before recomputing readiness, rather than continuously scheduling as individual steps complete. {8lneign5 @packages/kernel/src/execution/dbos-port.ts#runWorkflow @packages/kernel/src/execution/interpreter.ts#readySteps #architecture-current}

## Why
- Wave-at-a-time scheduling (not continuous) is deliberate: DBOS binds started child workflows positionally by (callerID, callerFunctionID) rather than by the requested workflowID, so replay launch order must exactly match first-run launch order or two steps can swap DBOS handles and the run stalls forever. {iyq8oiso @packages/kernel/src/execution/dbos-port.ts#runWorkflow #architecture-current}
