# packages/cli/src/runtime.ts

## Facts
- buildRuntime's stepTools closure builds commitTool with `dir: p.workspaceDir` (the running step's own checkout), not `config.dir` (the supervisor's) — a task whose workspace is a separate orc worktree previews and commits into that worktree, matching where bindStepKnowledge and execTool already read/write. {1ad9qzuh @packages/cli/src/runtime.ts#buildRuntime.port.stepTools}
- packages/cli/src/runtime.ts's buildRuntime() assembles the step tool set inside its stepTools closure from the bound knowledge and decision tools (bindStepKnowledge), splitTool, readAnnotationsTool, reportCoverageTool, scopedChangesTool, taskPlanTool, commitTool, execTool, planNoteTools and finalizePlanTool; each factory gates itself on the step's role and config, and no step gets a memory tool. {e7lia86n @packages/cli/src/runtime.ts#buildRuntime.port.stepTools}

## Why
- The commit step's git_commit/commit_preview pair must run against the STEP's own checkout (p.workspaceDir), never the supervisor's config.dir: one supervisor serves every workspace at once, and a step whose task runs in an orc worktree writes its knowledge/decision files and its source changes into that worktree — pointing commitTool at config.dir instead made it preview/commit the supervisor's own checkout, where the floor paths mostly do not exist, so git_commit silently committed nothing and the worktree's real changes were never captured, with nothing reporting the mismatch. {mb790j3d @packages/cli/src/runtime.ts#buildRuntime.port.stepTools @packages/kernel/src/execution/commit-tool.ts#commitTool}
